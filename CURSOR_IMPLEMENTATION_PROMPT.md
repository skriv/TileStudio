# Промт для Cursor — разработка Tile Studio

> **Как использовать:** открой в Cursor пустой репозиторий (или существующий проект) и вставь **весь текст ниже** в Agent mode. Рядом с этим файлом передай `TILE_STUDIO_SPEC.md` и оригиналы `room_scheme.pdf`, `280.png`, `450.png`. Если в репозитории уже есть код, сначала изучи его и адаптируй решение без ненужной перезаписи.

---

## Роль

Ты — senior frontend / graphics engineer и архитектор браузерных 2D/3D-редакторов. Построй **работающее приложение**, а не презентацию, макет без поведения или набор заглушек.

Разрабатываем **Tile Studio** — браузерный редактор помещения и фотореалистичной раскладки плитки. Полное техническое задание находится в `TILE_STUDIO_SPEC.md`; оно является **источником истины**, а данный промт — инструкцией по исполнению. При конфликте подробных требований применяй спецификацию. Не придумывай неподтверждённые размеры или назначения плитки.

## Контекст и утверждённые решения

- Только веб-приложение; desktop-first, русский UI.
- Первый пилот: **только кухня (верхняя левая комната), туалет (верхний центр) и коридор (справа от них)** с пользовательского чертежа `room_scheme.pdf`. **Другие комнаты не моделируй.**
- Высота потолка **2400 mm**.
- Поддерживаются PDF-чертежи и фотографии/сканы планов; масштаб калибруется по известной длине, геометрия редактируется вручную.
- Мебель **не добавлять**.
- Пользователь **сам** создаёт статичные зоны на полах и стенах, затем **сам** назначает каждой зоне плитку. **Не назначай материалы по комнатам автоматически.**
- Главный приоритет — убедительная фотореалистичная картинка, **но нельзя подменять точную раскладку генерацией изображения**.
- Физические размеры: `280.png` — одна плитка **285 × 85 mm**; исходный файл 170×570 px, поэтому естественная ориентация **85 × 285 mm** и для горизонтальной кладки нужен поворот на 90°. `450.png` — **одна плитка 450 × 450 mm с целым чёрно-белым шахматным рисунком**; её внутренние квадраты НЕ являются отдельными плитками.
- Файлы плиток использовать оригинальные, не перерисовывать, не обрезать, не растягивать и не заменять похожими.

## Цель твоего текущего запуска

Не ограничивайся документацией. Реализуй **как можно больше полноценного MVP за текущую сессию**, начиная с работающего вертикального среза:

1. Запускаемый Vite + React + TypeScript проект с аккуратным UI.
2. Импорт и показ плана (PDF/изображение), ручная калибровка, построение 2D-контура.
3. Простая 3D-комната с реальной высотой 2400 mm из подтверждённых контуров.
4. Выбор пола/стены и ручное создание **статичных зон**.
5. Импорт исходных материалов с точным размером и независимое назначение каждой зоне.
6. Геометрически корректная укладка, подрезки, отдельные швы и UV, сохраняющие рисунок.
7. Интерактивный 3D Preview с реальными материалами и светом.
8. Реальная функция качественного Photo Render (на доступной технологии) или честно обозначенный renderer limitation, без фальшивого рендера.
9. Сохранение проекта и экспорт реального изображения.
10. Математические тесты и инструкции запуска.

Если объём большой, сначала реализуй **работающую вертикальную цепочку:** создать/открыть план → обвести/выбрать помещение → создать зону → выбрать плитку → увидеть точную раскладку → экспортировать изображение. Далее развивай остальные функции. Не останавливайся на скелете приложения.

## Подход к реализации

### 1. Проверь исходники и проект

- Изучи `TILE_STUDIO_SPEC.md` целиком и проверь наличие `room_scheme.pdf`, `280.png`, `450.png` в текущем workspace.
- Если исходники есть, перенеси/скопируй их в `public/samples/`, не изменяя бинарники. Если исходников нет, **не генерируй подмену**: реализуй импортер и напиши, куда пользователь должен положить реальные файлы; при этом приложение должно оставаться работоспособным на создаваемых вручную помещениях.
- Исследуй текущие package.json, дизайн-систему и окружение; не удаляй рабочий код, если проект уже существует.
- Выбери стабильные совместимые версии зависимостей. Не внедряй непроверенные нативные/серверные зависимости ради одного эффекта.

### 2. Архитектура

Используй:

- React, TypeScript, Vite;
- Three.js + `@react-three/fiber` (и `@react-three/drei`, если полезно);
- PDF.js для показа PDF в браузере;
- изолированное ядро `core/geometry` и `core/tiling` **без зависимости от React**;
- IndexedDB (или надёжную компактную обёртку) для сохранения проекта, включая Blobs изображений;
- Vitest для численных тестов;
- модульность и строгую типизацию; без `any` там, где это можно избежать.

Предпочтительная модель: `Project -> Room -> Surface -> Zone -> Assignment(Material + TileLayoutSettings)`. В библиотеки материалов хранятся изображения одной физической плитки, их размер и оптические параметры. Для каждой зоны отдельный `Assignment`.

В 2D/geometry все координаты — **mm**; в Three.js преобразуй `mm / 1000` в метры единой функцией. Источник истины — mm.

### 3. Сцена и ввод плана

- Показывай PDF/изображение в качестве подложки в 2D редакторе. Поддержи pan/zoom и калибровку двумя точками по известному отрезку (задать длину в mm).
- Построй удобную ручную обводку замкнутого контура; клики по точкам, snap, редактирование/удаление вершин, завершение и отображение размеров.
- Создай или загружай 3 помещения строго из списка: `Кухня`, `Туалет`, `Коридор`. Не придумывай их готовые полигоны по PDF: точные контуры пользователь обводит сам.
- Обеспечь построение стен и пола из каждого подтверждённого контура, базовая высота 2400 mm.
- Отдельно показывай режим создания проёмов; неизвестная высота дверей должна быть явно редактируемой, а не якобы считанной из документа.
- Если работаешь над PDF-фоном, остальные помещения могут быть на изображении, но **не создавай для них 3D-сцену**.

### 4. Статичные зоны

- Выбери комнату → конкретный пол/стену → `Создать зону`.
- Зоны: вся поверхность, прямоугольник, ручной полигон; размеры/границы в mm.
- Для стен локальная плоскость: `u` вдоль стены, `v` по высоте от чистого пола. Для пола: локальные 2D координаты.
- После создания зоны фиксированы, пока пользователь явно не перешёл в `Редактирование зон`.
- Выбор другого материала меняет только назначение (`Assignment`), **не границы зоны**.
- Не присваивай `280.png` или `450.png` ни одному помещению по умолчанию; зоны исходно «Без материала».
- Зоны должны быть видимы и выбираемы в 2D и 3D (разумный hit test или tree selection).

### 5. Реальный движок плитки: обязательные математические правила

**Это критическая часть. Не заменяй её `texture.repeat` по всей поверхности.**

- Строй экземпляры физических плиток по локальной сетке поверхности: шаг `(tileWidthMm + groutMm, tileHeightMm + groutMm)`.
- Поддержи начальную точку, ориентацию 0/90°, ширину и цвет шва; затем, если успеваешь, сдвиг ряда 1/2 и 1/3, поворот сетки и центрирование.
- Обрезай каждую плитку геометрически по границам зоны, внутренним углам и проёмам; применяй robust polygon clipping там, где нужно.
- Вычисляй UV относительно **полной исходной плитки**. Если плитка подрезана, на ней должен быть правильный кусочек рисунка, а не вся исходная картинка, ужатая в подрезку.
- Не делай межплиточный шов внутри белых/чёрных квадратов `450.png`. Весь файл — **одна** плитка 450×450 mm.
- Поворот `280.png` на 90° разрешён и необходим для ориентации 285×85 без искажения изображения.
- Не менять физический размер плиток ради попадания в размеры комнаты.
- Сохраняй tile-instance ID, координаты и данные подрезки, чтобы были тестируемы значения, а не только пиксели на экране.

Тест-кейсы, которые обязаны пройти:

```text
2500×2500 mm, плитка 500×500 mm, шов 0 mm, старт от угла:
  5×5, 25 полных плиток.

2500×2500 mm, плитка 500×500 mm, шов 2 mm, старт от угла:
  5×5 позиций, крайние подрезаются (500×5 + 2×4 = 2508 mm).

900 mm ширина, плитка 450 mm, шов 0:
  2 полные плитки в ряд.

900 mm ширина, плитка 450 mm, шов 2:
  нужны подрезки, нельзя «втиснуть» две целые и шов в 900 mm.

450.png:
  один полный узор соответствует одному экземпляру 450×450 mm;
  3×3 или другая внутренняя сетка изображения не создаёт 9 физических плиток.

280.png:
  170×570 px соответствует портретной ориентации 85×285 mm;
  при повороте на 90° получаем 285×85 mm без crop и stretch.
```

### 6. 3D и визуализация

- Сделай нейтральные пустые комнаты, физически корректные масштабы, разумные материалы стен и потолков, свет из окон / общий свет.
- 3D viewport — основной и самый большой элемент интерфейса.
- Камера orbit/pan/zoom, предустановки видов, приоритет перспективному просмотру с человеческой высоты; предоставь вид сверху и возможность скрыть стены/потолок.
- Быстрый `3D Preview`: реальные UV, PBR материалы, мягкие тени, корректный цвет, без placeholder-панорамы.
- Отдельный `Photo Render`: попытайся реализовать фактический прогрессивный физически корректный браузерный рендер, после проверки совместимости техники с библиотеками и GPU. **Не утверждай, что реализован path tracing, если он не работает**. Если пока есть только качественный raster rendering, открыто обозначь его как качественный preview, запиши ограничение и оставь интерфейс/архитектуру для фото-режима.
- Экспортируй фактическое изображение WebGL/canvas или фактический Photo Render без подмены и без image-to-image AI.
- Любая смена материалов должна сохранять геометрию и позиции камеры.

### 7. UX и стилистика

Создай продуманный лаконичный рабочий инструмент, не стандартную «admin dashboard» страницу:

- Слева: комнаты, поверхности, зоны, библиотека плитки.
- Центр: максимально большой viewport, с переключателем `План / 3D / Рендер`.
- Справа: параметры выделенной зоны/материала/света/камеры.
- Чёткое состояние выбранной зоны; выделение зоны в сцене и дереве синхронизированы.
- Не перегружай интерфейс карточками и большими пояснениями; делай плотную профессиональную панель инструментов.
- Доступны состояния: без плана, без калибровки, без геометрии, без зоны, без материала, ошибка рендера.
- Все параметры вводятся в **mm**, явно показывай единицы.
- Для `450.png` в превью показывай цельное изображение одной плитки, а не картинку из девяти отдельных tiles.

### 8. Сохранение

- Храни целиком проект, в том числе бинарные изображения материалов.
- Поддержи сохранить/открыть без потери настроек; привяжи данные к `schemaVersion`, чтобы дальнейшие изменения были мигрируемыми.
- Поддержи экспорт PNG/JPG реального вида.
- Если реализуешь импорт/экспорт файла проекта, он должен быть переносимым — никаких абсолютных путей к файловой системе или временных Object URL в сериализации.
